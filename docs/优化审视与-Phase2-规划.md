# 优化审视与 Phase 2 规划

本文分三部分：功能对照 Setlog 的缺口收敛情况、当前架构的优化与故障预防清单、Phase 2（多人 Log）的落地规划。

---

## 一、功能对照 Setlog：本轮补齐了什么

| Setlog 能力 | 补齐前 | 现在 |
|---|---|---|
| 站内回看当天记录 | **完全缺失**（能拍能合成，但在 App 里看不了） | 全屏播放器，当天素材自动连播；点某一格从那条开始放 |
| 可视化的日历 / 归档 | 只有一列文字（`14:30 · 5.2 秒`） | 缩略图横向条 + 往期三列网格，封面来自当天第一条素材 |
| 一日详情 | 无 | 一日详情页：合成结果播放 / 存相册 / 分享 + 当天素材网格 |
| 删除素材 | Repository 有方法但 UI 没入口 | 素材详情面板可删（级联删留言 + 让当天合成失效） |
| 前后摄切换 | 无（固定后摄） | 有；录制中禁用避免打断 |
| 录制时长可见 | 无 | 录制中显示计时徽标 |
| 提醒不打扰 | 每小时提醒会在凌晨响 | 活跃时段窗口（默认 9:00–22:00）+ 随机间隔档位 |
| 记录成就感 | 无 | 连续记录天数 + 累计天数 |
| 存储可控 | 无 | 「我的」页显示日志占用，可一键清缓存与残留 |

时长依然不限时（按需求保留），但录制画质钉在 720p——不限时长 + 不限画质会让单条素材轻易上 GB。

## 二、数据存储优化

### 已落地

- **分层存放**：元数据在 Room，视频在 app 私有目录（免存储权限），按 `yyyy-MM-dd` 归档。
- **按日聚合查询**：归档页用一条 `GROUP BY dayEpoch` 的聚合 SQL（含封面路径子查询）拿到条数、总时长、封面，而不是把全部 clip 拉进内存再分组。
- **缩略图两级缓存**：内存 LRU + 磁盘 JPEG（320px），磁盘上限 40MB，超限按最旧淘汰；内存层按实际 ARGB 字节限制为 16MiB，最多两路并发解码。
- **写入原子性**：合成先写 `.tmp` 再改名。否则中途被杀会留下一个「文件存在但播不了」的半截合成，而新鲜度判断正是看文件是否存在。
- **录制画质上限**：720p（`QualitySelector` + `FallbackStrategy`），从源头控制体积。
- **空间闸门**：可用空间低于 300MB 拒绝开录，避免写满磁盘产生损坏文件。
- **启动自愈**：清理不在册的孤儿文件；带三道保险（库里查不到素材就放弃、只清 6 小时前的文件、待删数量超过在册数量就中止），防止「路径失配 → 全量误删」。
- **备份策略**：云备份排除视频、保留数据库与设置。
- **迁移安全**：`fallbackToDestructiveMigration()` 只在 debug 生效。
- **保留策略**（本轮补齐，收益最大的一项）。永久 / 7 天 / 30 天三档；到期且**已有可播合成**的日期才会被清，清理只删原始视频文件，clip 记录、说明、留言全部保留（`log_clips.sourceKept = 0`）。Setlog 原版本质就是把一天压成一条，这是数量级的空间节省。一日详情页另有手动「立即清理」。
- **相对路径**（本轮补齐）。`filePath` 改存相对 `dailylog/` 的路径，Repository 是唯一的转换切面：读出即绝对路径、写入即相对路径，上层代码无感。首启做一次性归一化，压不成相对路径但文件仍在目录里的按文件名重定位，两者都失败则保持原样（不靠猜测改写用户数据）。
- **孤儿判定改按文件名**。按完整路径比对时，一次挂载点变化就会让全部素材同时"失配"，那种情况下删除等于清空用户记录。

### 建议继续做（按性价比排序）

1. **开 `exportSchema` 并加 Room 迁移测试**（`MigrationTestHelper`）。现在关掉了 schema 导出，迁移写错只能靠真机升级才发现——数据库已经到 v10 且 release 不再允许推平重建，这一项的性价比升高了。
2. **手动备份 / 导出**。把数据库 + 设置 + 选定日期的视频打成一个 zip 让用户自己存。云备份靠不住，这是唯一能对抗「手机丢了」的手段。
3. **保留策略再进一步**：清理前把当天的封面缩略图固化保存（现在清理后归档封面回落到合成结果，够用但不是最优）；以及「按占用上限清理」而不是只按天数。
4. **SharedPreferences → DataStore**。异步、有事务语义，比 `apply()` 更稳。优先级低。
5. **磁盘写入失败的兜底**。空间写满时 SQLite 会抛 `SQLiteFullException`，目前没有统一捕获，建议在 Repository 写操作层包一层并给出可读提示。

## 三、一个软件通常还应该有的优化

### 性能

- 启动路径：Room 初始化与所有 IO 已经在 App 作用域协程里，主线程只做 UI。可在 debug 打开 `StrictMode` 主动暴露主线程 IO。
- 列表：缩略图异步解码 + 稳定 key 已做；素材很多时可加预取与分页（当前一天几十条量级不需要）。
- 内存：缩略图统一缩到 320px；内存 LRU 已按实际 ARGB 字节限制为 16MiB，后台或系统内存紧张时主动缩减/清空。
- 播放：`ExoPlayer` 随页面创建/释放；若将来做瀑布式浏览，应复用单实例并预缓冲。
- 包体：release 目前 `isMinifyEnabled = false`，加上 `material-icons-extended` 后包会明显变大，建议开启 R8 + `shrinkResources`。

### 体验

- 三态齐全：加载 / 空 / 错误。当前空态齐了，加载态多数直接显示空列表（一日详情页已用 `null` 区分「未加载」与「真的空」）。
- 无障碍：大量 `contentDescription = null`，图标按钮应补文案。
- 大字体 / 深色模式：深色已做；超大字号下的网格与徽标还需实测。
- 反馈：合成有百分比进度与终态提示；删除有二次确认；录制按钮有形变动画。

### 工程

- 崩溃可见：本机崩溃日志落盘 + 可分享（已做）。没有服务端时这是唯一能回答「昨天为什么闪退」的手段。
- 本地指标：合成成功/失败次数、平均耗时、素材总数，写进「我的」页的诊断区，用来判断问题是偶发还是必现。
- 测试分层：纯逻辑单测（连续天数、提醒时段推算、格式化已覆盖）→ Room 迁移测试 → 关键路径 UI 冒烟测试。
- 统一日志开关：release 关闭调试输出。

## 四、故障预测与防 bug 清单

### 本轮已修的真实缺陷

| # | 问题 | 后果 | 处理 |
|---|---|---|---|
| 1 | 每小时提醒不分昼夜 | 凌晨被通知叫醒 | 活跃时段窗口，落在窗口外顺延 |
| 2 | 开机后不重排提醒 | 重启一次提醒永久失效 | `BootReceiver` 补排 |
| 3 | Android 12+ 撤销精确闹钟权限 | `setExactAndAllowWhileIdle` 抛 `SecurityException` | 先探测再降级为非精确闹钟，双层 `runCatching` |
| 4 | 合成后新增素材不会重合成 | 「合成」按钮点了没反应，看到的是旧视频 | 用最后一条素材时间与合成时间比对判断过期 |
| 5 | 合成任务挂在页面作用域 | 切 Tab / 返回就取消，白等一场 | 移到 App 作用域 + `Mutex` 保证同时只有一个 |
| 6 | 关闭说明弹窗直接丢弃录制 | 刚拍的视频没了，只留孤儿文件 | 关闭即按「无说明」保存，删除需显式点击 |
| 7 | 相机 provider 不解绑 | 页面退出后相机仍被占用 | `onDispose` 里 `unbindAll` |
| 8 | 录制画质取设备最高 | 部分机型 4K，几分钟吃掉数 GB | 钉在 720p |
| 9 | 空间不足照常开录 | 写满磁盘 + 损坏文件 | 录前空间闸门 |
| 10 | 误触产生 0.2 秒废片 | 污染当天合成 | 低于 0.8 秒丢弃 |
| 11 | 跨零点录制归档错位 | 素材落到第二天，与文件目录不一致 | 以录制开始时刻定日期；页面每分钟复核「今天」 |
| 12 | `logId` 竞态 | 首启即拍会写入 `logId = -1`，素材永久不显示 | 落库前兜底 `ensurePersonalDailyLog()` |
| 13 | Android 9 及更早导出静默失败 | `RELATIVE_PATH` 是 Q 才有的字段 | 能力探测，老系统只显示「分享」 |
| 14 | 半截合成文件被当成有效结果 | 播放黑屏且不会自动重合成 | 临时文件 + 改名 |
| 15 | 删除素材残留留言与过期合成 | 数据不一致 | 级联删除 |
| 16 | Release 允许推平重建数据库 | 漏写迁移会静默清空全部数据 | 仅 debug 允许 |
| 17 | 一日详情页首帧空列表即退出 | 页面点开就弹回 | 用 `null` 区分「未加载」与「空」 |
| 18 | 孤儿清理可能全量误删 | 路径一旦失配等于清空用户记录 | 三道保险 |
| 19 | 通知被关闭时提醒静默失效 | 用户以为 App 坏了 | 提醒面板显式警示并可跳系统设置 |
| 20 | 云备份含视频 | 超出备份上限导致整体备份失败 | 备份规则排除视频 |
| 21 | `PlayerView` 的 `player` 属性遮蔽外层同名变量 | `apply { this.player = player }` 实际是自赋空值，播放器永远黑屏 | 外层变量改名 `exoPlayer`，改用 `also` 显式引用 |
| 22 | App 还活着时点提醒通知无反应 | `activity.intent` 不是 Compose 可观察状态，`onNewIntent` 不触发重组 | 用 `mutableStateOf<Intent?>` 承载待跳转意图，消费后置空 |
| 23 | 强制重合成先删旧合成再查素材 | 已按保留策略精简的日期会被删掉唯一剩下的合成结果，那一天彻底消失 | 先查素材，没有可用素材时原样保留已有合成 |
| 24 | 保留策略可能清掉没合成的日期 | 不可逆的数据丢失 | 候选日期用 `INNER JOIN daily_compilations` 取，且执行前复核合成文件存在且非空 |

### 尚存风险（按优先级）

1. **厂商杀后台**（小米 HyperOS 尤其明显）：提醒与后台合成都可能被推迟。缓解手段只有引导用户开自启动/后台无限制，值得在提醒面板里加一段说明与跳转。
2. **保留策略与合成的时序**：保留策略必须永远排在「补合成」之后（启动流程与 `DailyCompileWorker` 都已按此顺序）。将来若新增任何触发入口，这个先后关系是不能破的约束——反过来就是删掉还没合成的原始素材。
3. **Transformer 混合规格拼接失败**：不同分辨率/编码/帧率的素材拼在一起，个别机型会报错。现在只是提示失败，稳妥做法是失败后降级为「统一转码到 720p 再拼」。
4. **长时间素材合成耗时**：一天几十条长视频合成可能几分钟，进程被系统回收就白做。应改为前台服务 + 通知进度。
5. **磁盘写满时数据库异常**未统一捕获。
6. **无障碍文案缺失**。

## 五、Phase 2 规划：多人 Log

目标：一个 Log 可以有多个成员，各自拍摄，一天结束后汇总成一条「大家的今天」。当前采用**无云服务器的附近模式**：一台手机用 `LocalOnlyHotspot` 成为临时权威节点，所有转码仍留在客户端，原片默认留在拍摄设备。

### 5.1 范围划分

| 能力 | Phase 2 是否做 | 说明 |
|---|---|---|
| 账号 | 做，最轻量 | 设备生成密钥对，服务端只存公钥与昵称，不做手机号/邮箱注册 |
| 创建 Log / 邀请码加入 | 做 | 6 位邀请码，服务端校验后把成员写入 Log |
| 素材元数据同步 | 做 | 谁在哪天几点拍了一条、时长、说明 |
| 素材文件同步 | 做，但按需流式 | 默认只同步缩略图；原始视频留在拍摄设备，播放时由主机转发 HTTP Range，不先完整下载 |
| 服务端转码/合成 | **不做** | 小服务器扛不住，合成在成员的手机上做 |
| 留言 / 表情回应 | 做 | 已有 `log_comments` 表结构，加 `remoteId` 与作者标识 |
| 实时推送 | 不做 | 轮询 + 打开 App 时同步即可，省服务器 |

### 5.2 数据模型改动

现有表已为多人预留了字段（`daily_logs.inviteCode`、`log_comments.authorName`），Phase 2 需要补：

- `daily_logs`：`remoteId`、`role`（owner/member）、`memberCount`、`lastSyncedAt`
- `log_clips`：`remoteId`、`authorId`、`uploadState`（本地/上传中/已上传/失败）、`remoteThumbUrl`、`remoteVideoUrl`
- 新表 `log_members`：`logId`、`authorId`、`nickname`、`avatarSeed`
- 新表 `sync_outbox`：待上传/待确认的操作队列，保证弱网下不丢操作

数据库版本从 10 → 11，写正式迁移（release 已禁用推平重建，必须写对）。

注意保留策略与同步的交互：`sourceKept = 0` 的素材本地已经没有原始文件，不能作为上传源。多人版要么在清理前完成上传，要么把「已精简」的天标成只同步合成结果。

### 5.3 同步策略

- **单向优先**：先做「我的素材上传 + 拉取他人元数据」，不做冲突合并。
- **幂等**：客户端生成 `clientId`（UUID），服务端按 `clientId` 去重，重试不会产生重复记录。
- **默认不上传原片**：成员设备运行只读素材源；热点主机只转发 Range 响应，固定使用 64KiB 应用缓冲，不生成临时副本。
- **可用性优先的可选缓存**（后续）：只有用户明确选择离线可用时才按块缓存，全部接收者确认后可删除缓存。
- **拉取时机**：打开 App、下拉刷新、成员触发合成前，不做常驻长连接。

### 5.4 多人合成

- 触发者在本机拉齐当天所有成员的素材后再合成，产物可选择上传给其他成员复用（避免每人各转一次）。
- 布局：成员 ≤ 4 用分屏网格（Media3 `Composition` 多 sequence + `VideoCompositorSettings`），否则退回顺序拼接。
- 合成必须在前台服务里跑，带通知进度。

### 5.5 附近主机最小形态

- 主人手机的前台服务内嵌局域网 HTTP 服务与 Room，不再部署独立进程。
- Android Keystore 生成设备身份；热点凭据 + 邀请码限制房间访问。
- `LocalOnlyHotspot` 本身没有 Internet；客户端 socket 绑定 NSD 返回的 Wi-Fi `Network`，不回落蜂窝网络。
- mDNS 不可用的 ROM 只探测 DHCP 明确给出的 Wi-Fi 网关与固定端口，不扫描整个网段。

### 5.6 建议实施顺序

1. ~~Phase 1 收尾：保留策略 + 相对路径迁移~~（已完成，多人版就是建在这个基础上）。
2. 账号与 Log 成员（纯元数据，不涉及视频）。
3. 元数据同步 + 缩略图同步（此时 UI 已能显示「今天有谁拍了」）。
4. 视频 Range 流式读取与主机固定缓冲转发。
5. 多人合成（分屏布局 + 前台服务）。
6. 留言/回应同步。

### 5.7 Phase 2A 当前进度（2026-08-12）

已实现：

- Room v10 → v11 正式迁移：多人 Log、成员、`sync_outbox`、`sync_events`、远端素材状态。
- 当前 Log 抽象；拍摄与合成文件按 Log 隔离，避免同一天互相覆盖。
- `LocalOnlyHotspot` 主机前台服务、NSD 广播与 Wi-Fi 网关回退发现。
- 创建/加入附近 Log UI；无云账号的 Android Keystore 设备身份。
- 成员元数据发布/拉取；拍摄完成后在线自动同步当天元数据。
- 成员只读素材源、主机 Range 中继、ExoPlayer 自定义私网 DataSource。
- 大文件 IO 固定 64KiB 缓冲。8 个并发连接时，应用层中继缓冲约 512KiB；不计系统 socket、播放器解码缓冲和最终合成文件。
- 远端缩略图按需生成与小文件缓存；主机和成员均不保存第二份完整原片。
- 留言、素材说明、删除墓碑的增量事件；成员 outbox 指数退避重试，主机按 operationId 幂等去重。
- 写操作由 Android Keystore 设备私钥签名，主机使用加入时的公钥验证，防止同热点成员冒充别人素材源。
- App 进入前台即自动 NSD + Wi-Fi 网关回退发现；已加入设备核对 remoteLogId 后自动握手、启动素材源和同步，首次设备只需手动输入一次邀请码。
- 房主邀请二维码包含热点凭据、remoteLogId 与一次邀请码；App 内 CameraX 扫码和 `nierlog://join` 外部入口都可接收，实际加入仍核对当前热点房间并做设备签名握手。
- 前台连接监督：12 秒签名心跳、3–30 秒断线退避恢复、24 秒当天元数据刷新；后台停止。统一状态卡给出 Wi-Fi、权限、认证或房主无响应的可操作提示。
- 成员面板显示在线人数与今日准备度；首页提供紧凑汇总，连接页显示每个成员的今日条数。
- 多人合成预检以最多 4 路并发 HEAD 验证素材源，不下载原片；离线时支持等待重检或跳过本次不可用素材，成员回线后可重新生成完整版。
- 存储页分类展示原片、合成、缩略图与残留，空间低于 300MB 时显式预警；安全清理不触碰在册视频。
- Media3 Transformer 直接消费私网 DataSource 做多人顺序合成；输入不落临时原片，失败时保留旧合成。
- 可重复自动压测：8 并发共 1GiB 虚拟流、10000 次断连、100000 个随机 Range、100000 次退避检查，并断言单路读写块始终不超过 64KiB。

尚未完成：
